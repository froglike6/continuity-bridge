# Continuity Bridge Protocol v1

Status: protocol version 1 with optional notification metadata and image
clipboard support. This document is normative. `fixtures/contract-cases.json`
is the machine-readable companion. Existing text and notification events remain
valid; richer producers require an upgraded relay and matching recipient app.

## 1. Scope and transport

Protocol v1 has exactly two authenticated roles: `android` and `macos`. Each
publisher has a stable device identity. The relay binds every bearer
token to one configured `role` and `deviceId`; a request body cannot change that
identity. HTTPS, token provisioning, and TLS trust are deployment concerns. The
protocol never logs tokens or payload values.

Endpoints:

| Method and path | Meaning | Success |
| --- | --- | --- |
| `GET /v1/health` | Process liveness and current relay identity | `200` |
| `GET /v1/ready` | Durable-state readiness and safe recovery attempt | `200`, or `503` while unavailable |
| `POST /v1/events` | Publish one event | `201`, or `200` for an identical retry |
| `GET /v1/events?after=CURSOR&waitMs=25000` | Fetch retained destination events | `200` |
| `POST /v1/acks` | Acknowledge successfully applied events | `200` |

`Content-Type` is `application/json; charset=utf-8`. Request JSON must be one
object. Duplicate JSON member names, malformed UTF-8, trailing data, non-finite
numbers, and malformed JSON are rejected. Unknown object fields are ignored at
every level and are excluded from identity fingerprints. Unknown protocol
versions and event kinds are rejected. There is no executable or instructional
payload interpretation: all strings, including instruction-like text, are opaque
UTF-8 data.

## 2. Event envelope and direction

Every event has these fields:

```text
protocolVersion  integer, exactly 1
eventId          non-empty string, <= 128 UTF-8 bytes
originDeviceId   non-empty string, <= 128 UTF-8 bytes
originRole       "android" | "macos"
originEpoch      non-empty string, <= 128 UTF-8 bytes
sequence         integer, 1..9007199254740991
kind             "clipboard.text" | "clipboard.image" | "android.notification"
createdAtMs      integer, 0..9007199254740991 (metadata only)
expiresAtMs      optional integer, createdAtMs..9007199254740991
payload          object defined below
```

The authenticated publisher must equal both `originRole` and the token-bound
`originDeviceId`. Allowed directions are exact:

| Publisher | Kind | Destination |
| --- | --- | --- |
| `android` | `clipboard.text` | `macos` |
| `android` | `clipboard.image` | `macos` |
| `android` | `android.notification` | `macos` |
| `macos` | `clipboard.text` | `android` |
| `macos` | `clipboard.image` | `android` |

No other role, direction, notification source, or notification destination is
valid in v1.

`clipboard.text` payload is `{ "text": string }`. Empty and multiline text are
valid. `text` is capped at 1,048,576 UTF-8 bytes. Rich text, arbitrary files,
URIs, and clipboard history are outside v1.

`clipboard.image` payload is `{ "mimeType": "image/png" | "image/jpeg",
"dataBase64": string }`. Base64 must be canonical standard Base64, with padding
where required, no whitespace, and no alternate alphabet. The decoded bytes
are capped at 8,388,608 (8 MiB); encoded length is capped at 11,184,812 bytes.
PNG must begin with its eight-byte signature and JPEG with `FF D8 FF`.
Transport validation does not establish that an image can be rendered: the
receiving OS adapter checks complete image syntax and bounded geometry before
applying it. Original bytes and MIME are preserved. Unsupported or oversized
source images remain in the local clipboard and produce a concise format/size
status; the bridge does not silently convert them to fit.

`android.notification` payload is:

```json
{
  "notificationKey": "stable Android StatusBarNotification key",
  "packageName": "Android package name",
  "appLabel": "resolved harmless display label",
  "title": "possibly empty title",
  "body": "possibly empty body"
}
```

The five required fields are strings. UTF-8 caps remain respectively 4,096,
255, 4,096, 8,192, and 65,536 bytes. Optional fields are:

| Field | Wire type and bound |
| --- | --- |
| `iconPngBase64` | Canonical standard Base64, at most 16,384 bytes; decoded PNG at most 12,288 bytes, PNG signature and first 13-byte IHDR with width and height each 1 through 128 |
| `progress` | Object with integer `value`, integer `max`, Boolean `indeterminate` |
| `isOngoing` | Boolean |
| `isRedacted` | Boolean |
| `category` | String, empty allowed, at most 128 UTF-8 bytes |

Progress integers range from 0 through 2,147,483,647 and `value <= max`.
When `max == 0`, `value == 0` and `indeterminate == true` are required.
Determinate progress requires a positive maximum. Unknown progress members are
excluded from normalization, just like unknown envelope and payload members.
Optional means absent; explicit null and wrong types are rejected.

Icons identify the source application, never a sender avatar. Producers should
rasterize the application icon at 64 pixels, reducing it when necessary, and
omit it when unavailable or when it would exceed the payload budget.
`isRedacted` is set from actually delivered redaction markers, never solely
because the Android device is locked.

The canonical JSON encoding of all known notification payload fields remains
capped at 81,920 UTF-8 bytes. JSON strings use ordinary JSON escaping without
escaping `/`. The whole event POST body is capped at 12,582,912 bytes (12 MiB).
Ack bodies remain capped at 65,536 bytes and contain at most 100 event IDs.

## 3. Ordering, identity, and retries

Wall clocks never order events. `createdAtMs` and `expiresAtMs` are metadata and
expiry hints only. The relay orders acceptance by `(originDeviceId,
originEpoch, sequence)` and assigns every first acceptance one monotonically
increasing persisted server cursor. Cursors are unsigned decimal strings (not
JSON numbers), beginning at `"1"`; `"0"` means no event seen.

For an active `(originDeviceId, originEpoch)`, the next new event sequence must
be greater than the persisted high-water sequence. A lower sequence is stale.
Reuse of the same sequence with different normalized content is a conflict. A
device changes epoch only after it has durably abandoned the previous epoch and
starts the new epoch at sequence 1. Accepting that sequence retires the prior
epoch; later traffic from a retired epoch is stale. Event IDs must be unique.

The normalized identity contains every known envelope and known payload field,
but no unknown field. A retry identical after normalization returns HTTP 200,
`idempotent: true`, and the original cursor; it creates no second retained
event. Reusing an event ID with different normalized content yields 409
`event_id_conflict`. Reusing an origin epoch/sequence with different content
yields 409 `sequence_conflict`. Other old or retired ordering yields 409
`stale_sequence`. Dedupe fingerprints are persisted for the newest 4,096
accepted identities, counted by server cursor, plus every still-retained event
outside that window. Retained identities do not consume the 4,096 recent-retry
slots. With at most 100 retained notifications and at most 64 retained sender
clipboards, the union is bounded by 4,260 fingerprints. ACK, expiry, eviction, and clipboard
supersession remove an extra fingerprint in the same committed state change
that removes its event; an identity still inside the recent window remains.
After eviction, the persistent sequence high-water still prevents an old
sequence from becoming new.

## 4. Relay retention and cursors

The relay durably owns `serverEpoch`, `nextCursor`, active/retired origin epochs,
sequence high-waters, bounded dedupe fingerprints, retained destination events,
and ack state. Normal restart reloads all of them, so `serverEpoch` and cursor
values do not change. A deliberate empty-state replacement creates a new random
`serverEpoch` encoded as 32 lowercase hexadecimal characters (16 random bytes)
and resets the tail cursor to `"0"`. On epoch mismatch a client
sets its fetch cursor to `"0"`; it does not discard its outbox or applied-ID
state.

Relay and clients retain at most 64 distinct replay origin keys. A restored
state with more than 64 keys is corrupt. At 64 keys, an event for a new origin
epoch is rejected before apply, acknowledgement, cursor advance, or state
mutation; an event advancing an already retained key remains eligible.
Implementations must not evict an old replay origin key to admit a new one.

`GET /v1/events` accepts `after` as a canonical unsigned decimal string and
`waitMs` as an integer from 0 through 25,000. The authenticated role receives
only its destination events with cursor greater than `after`, ascending by
server cursor. Each encoded fetch response is capped at 12,582,912 bytes.
If the next retained event would exceed the page budget, `nextCursor` is the
cursor of the last included event; the next fetch resumes there. Otherwise
`nextCursor` is the persisted server tail, even when no retained event is
returned. An accepted individual event always fits on an otherwise empty page.
A request at the tail may be held for at most `waitMs` and
then returns an empty list. An earlier cursor can replay any still-retained,
unacknowledged event. Cursor gaps caused by ack, expiry, eviction, or clipboard
supersession are normal.

Clipboard is one latest-value register per sender device. Text and image share
that register: either kind immediately supersedes and removes the sender's older
unacknowledged clipboard, including across type changes. Other senders retain
their own latest values. Only each retained latest value is at-least-once.

Notifications are retained individually. Server receipt time, never client
clock ordering, sets a maximum lifetime of 900,000 ms. A valid `expiresAtMs`
may request earlier expiry but never extends that lifetime. Across pending
notifications the relay retains at most 100 events and 524,288 canonical event
JSON bytes. Before every mutation/fetch it removes expired entries, then evicts
the smallest cursor until both bounds hold. Clipboard bytes are not counted in
the notification pool, and neither clipboard kind is expired or evicted as
notification history.

## 5. Ack timing and client-owned durable state

Ack request:

```json
{
  "protocolVersion": 1,
  "recipientDeviceId": "device bound to the bearer token",
  "recipientRole": "android or macos",
  "eventIds": ["one or more event IDs"]
}
```

The relay verifies that every known ID is destined for the authenticated role.
Unknown/already-removed IDs are safely reported, not recreated. Success body is
`{"acked":[...],"alreadyAbsent":[...]}`. Ack is idempotent.

Clients durably own a stable device ID, current origin epoch, next sequence,
full outbound outbox events, relay `serverEpoch`/cursor, and the newest 4,096
applied event IDs. An outbound event ID/epoch/sequence/content is persisted
before its first POST and never changes across retries. A `201` first acceptance
or `200` identical-retry response proves relay durability, records the original
cursor, and removes the sender outbox entry. Recipient `POST /v1/acks` state is
separate and never reaches back into the sender's local outbox.

Receipt is not application. A clipboard recipient acks only after the system
clipboard write is verified, the event-ID correlation marker is installed, and
the applied ID is durable. A macOS notification recipient acks after its permitted
local handling succeeds and the applied ID is durable; a user-blocked app may
be acknowledged without displaying or retaining its sensitive content.
Unresolved permission denial, write/add failure, cancellation, or failure to
persist withholds ack, so fetch redelivers. On redelivery an already-applied ID
must not duplicate the surface effect; after confirming durable applied state it
may ack. Echo suppression is by event ID marker, never content. A later manual
copy of identical text or image bytes is a new outbound event.

Client outboxes apply the same bounds as relay admission: one newest clipboard
per sender across text/image and Android notification entries capped at 100/524,288 bytes.
Notification overflow removes expired then lowest sequence; it never changes
the identity of a retained retry.

## 6. Responses

Representative success bodies (unknown response fields must be ignored):

```json
{"protocolVersion":1,"status":"ok","serverEpoch":"opaque","tailCursor":"0"}
{"accepted":true,"eventId":"evt","cursor":"1","serverEpoch":"opaque","idempotent":false}
{"protocolVersion":1,"serverEpoch":"opaque","after":"0","nextCursor":"1","events":[{"cursor":"1","event":{}}]}
{"acked":["evt"],"alreadyAbsent":[]}
```

All errors use `{"error":{"code":"stable_code","message":"safe metadata-only message"}}`.
No error body echoes payloads or bearer tokens.

The `message` strings below are exact. Authentication happens before body parsing,
so an unauthenticated malformed request is `401`, not a body oracle.

| Status | Stable code | Exact `message` |
| --- | --- | --- |
| 400 | `malformed_json` | `Malformed JSON.` |
| 400 | `invalid_event` | `Invalid event.` |
| 400 | `invalid_ack` | `Invalid acknowledgement.` |
| 400 | `invalid_query` | `Invalid query.` |
| 400 | `unsupported_protocol_version` | `Unsupported protocol version.` |
| 400 | `unsupported_kind` | `Unsupported event kind.` |
| 401 | `unauthorized` | `Unauthorized.` |
| 403 | `identity_mismatch` | `Authenticated identity does not match the body.` |
| 403 | `direction_forbidden` | `Event direction is forbidden.` |
| 409 | `event_id_conflict` | `Event ID conflicts with an accepted event.` |
| 409 | `sequence_conflict` | `Origin sequence conflicts with an accepted event.` |
| 409 | `stale_sequence` | `Origin sequence or epoch is stale.` |
| 413 | `payload_too_large` | `Payload is too large.` |
| 500 | `state_error` | `Persistent relay state is unavailable.` |

The fixture runner reports HTTP-equivalent statuses. It is not relay runtime or
network code and uses no secrets, dependencies, certificates, or private data.
