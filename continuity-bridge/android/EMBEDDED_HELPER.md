# 브리지에 내장된 클립보드 도우미

현재 Android 빌드는 별도 Shizuku 관리자 없이 브리지 APK 하나로 동작합니다. 이 휴대폰의 무선 디버깅에 앱이 직접 페어링하고, shell UID 2000의 클립보드 도우미를 실행합니다. 복사할 때 Activity나 오버레이를 띄우지 않습니다.

## 처음 연결

1. Android 11 이상에서 연속성 브리지를 설치하거나 기존 앱 위에 업데이트합니다. 같은 패키지와 서명을 사용하면 서버 설정과 인증 정보가 유지됩니다.
2. 브리지의 **클립보드 도우미 설정**을 열고 **개발자 옵션 열기**를 누릅니다.
3. Android의 **무선 디버깅**을 켭니다. 본인이 신뢰하는 Wi-Fi에서만 네트워크 허용 여부를 선택합니다.
4. 최근 앱 화면에서 Android 설정과 브리지를 **분할 화면**으로 엽니다. 설정의 **페어링 코드로 기기 페어링**을 누릅니다.
5. 그 창을 열어 둔 채 브리지에 6자리 코드를 입력하고 **코드로 연결**을 누릅니다. 포트는 자동으로 찾습니다. 검색에 실패할 때만 코드 창에 표시된 페어링 포트를 입력합니다.
6. 홈에서 공유 서비스를 시작하고 **텍스트·사진 공유**의 감지 상태를 확인합니다. 도우미 연결 표시와 실제 복사 감지 상태는 구분됩니다.

무선 디버깅 기본 화면의 연결 포트와 페어링 코드 창의 포트는 다릅니다. 설정을 전체 화면으로 전환하면 페어링 창이 닫힐 수 있으므로 최초 연결에는 분할 화면이 필요합니다. 코드는 저장하거나 로그에 남기지 않습니다.

별도 알림 권한이나 오버레이 권한은 최초 페어링에 필요하지 않습니다. Android 알림 전달에는 기존 알림 접근 권한이 필요합니다. Android가 표시하는 무선 디버깅 상태나 클립보드 접근 안내는 운영체제의 표시입니다.

## 재부팅과 재연결

**Android 13 이상**에서 **재부팅 후 자동으로 다시 연결**을 선택할 수 있습니다. 선택하면 최초 로컬 ADB 연결을 통해 브리지에 `WRITE_SECURE_SETTINGS`를 부여합니다. 앱이 무선 디버깅 설정을 켜고 저장된 키로 자신의 도우미를 다시 실행하기 위한 권한입니다.

자동 복구 조건은 다음과 같습니다.

- 재부팅 전 공유 서비스가 실행 중이었고 자동 복구가 켜져 있어야 합니다.
- 재부팅 후 첫 잠금 해제가 끝나고 Android에서 이미 허용한 Wi-Fi에 연결되어야 합니다.
- 브리지의 페어링 키와 Android의 해당 페어링 기록이 남아 있어야 합니다.

Android는 `adb_wifi_enabled`를 직접 변경해도 네트워크 신뢰를 검사합니다. 새 Wi-Fi는 시스템의 사용자 허용 절차가 필요하며, 앱은 이를 자동으로 승인하지 않습니다. 승인 대기 상태에서 주기적으로 허용 창을 다시 요청하지 않습니다. [AOSP의 네트워크 검사](https://android.googlesource.com/platform/frameworks/base/+/5ab3aa0c7b913079e1a8146d347faf66c49761a3/services/core/java/com/android/server/adb/AdbDebuggingManager.java#992)

홈에서 **중지**하면 다음 재부팅에도 자동으로 시작하지 않습니다. 직접 **시작**한 뒤에는 선택한 자동 복구 설정을 다시 사용합니다. Android에서 앱을 강제 종료한 경우에는 직접 앱을 다시 열어야 합니다. 제조사의 절전 정책이나 개발자 옵션 변경에 따라 직접 무선 디버깅을 켜거나 다시 페어링해야 할 수 있습니다.

저장된 연결을 해제하려면 Android의 **무선 디버깅 → 페어링된 기기 → Continuity Bridge → 삭제**를 사용합니다. 브리지의 자동 복구도 끄면 이후 재부팅 때 연결하지 않습니다. 새 연결에는 **새 페어링 코드로 연결**을 사용합니다.

## 연결 범위와 데이터

- 앱의 ADB 클라이언트는 `127.0.0.1`에만 연결합니다. 자동 검색도 이 휴대폰에 속한 주소만 허용합니다.
- ADB 키는 Android Keystore의 AES 키로 암호화해 앱 전용 저장소에 보관합니다. 다른 기기에 키를 전송하지 않습니다.
- 도우미 등록에는 shell UID와 매 실행마다 생성한 일회용 nonce를 모두 확인합니다. 도우미의 클립보드 IPC는 설치된 브리지 UID만 호출할 수 있습니다.
- 공개된 임의 명령 실행·파일 접근 API는 없습니다. 앱이 쓰는 shell 명령은 도우미 실행과 선택한 자동 복구 권한 설정으로 한정합니다.
- 텍스트와 PNG/JPEG 사진은 기존 릴레이·TLS·Cloudflare Access 경로를 사용합니다. 사진의 최대 크기는 8 MiB입니다. 이 기능 때문에 NPM이나 릴레이 설정을 바꿀 필요는 없습니다.
- 내부의 `ShizukuClipboard*` 클래스 이름은 기존 클립보드 구현을 이어 쓰는 이름입니다. 새 APK에는 외부 Shizuku SDK/provider가 포함되지 않습니다.

## 빌드와 테스트

저장소 루트에서 실행합니다. SDK/JDK와 서명 키 경로는 [빌드 안내](../BUILD.md)처럼 환경에 맞게 지정합니다.

```sh
./continuity-bridge/android/build.sh
./continuity-bridge/android/run-host-tests.sh
./continuity-bridge/android/run-embedded-lifecycle-tests.sh
./continuity-bridge/android/run-embedded-discovery-tests.sh
./continuity-bridge/android/build-tokenstore-test.sh
```

산출물은 `outputs/continuity-bridge-android-embedded-debug.apk`와 `.apk.sha256`입니다. 기존 Shizuku APK는 덮어쓰지 않습니다. 디버그 서명이므로 동일한 개발 키로 만든 기존 브리지의 업데이트로 설치합니다.

새 Android 계측 테스트는 `EmbeddedHelperInstrumentationTest`이며, 암호화된 키의 재사용, 외부 주소 거부, 일반 앱 UID의 도우미 등록 거부, 닫힌 페어링 세션의 시작 거부, 멈춘 TLS 연결 취소를 검사합니다. 테스트 APK는 제품 APK에 포함되지 않습니다.

## 의존성

libadb-android 3.1.1, SPAKE2 2.2.1, Conscrypt 2.7.0, Bouncy Castle 1.81을 사용하며 URL과 SHA-256은 [embedded.lock](dependencies/embedded.lock)에 고정합니다. APK에 라이선스 전문을 포함합니다. 변경한 페어링 소스는 [patches](dependencies/patches/)에 있습니다.

SPAKE2의 LGPL 조건을 포함한 출처·소스·재빌드 및 교체 방법은 [의존성 안내](dependencies/embedded-README.md)와 [라이선스 안내](dependencies/embedded-licenses/)에 있습니다. APK를 재배포할 때는 대응 소스와 재링크 자료도 함께 제공해야 합니다.

## 이번 검증의 범위

2026-09-13, 별도 Shizuku가 설치되지 않은 API 37 / arm64 / 16KB 페이지 에뮬레이터에서 다음을 확인했습니다. 격리된 TLS 릴레이와 테스트용 편집기를 사용했습니다.

- 시스템의 실제 페어링 코드 창과 브리지를 분할 화면으로 열어 연결했습니다. 호스트 Mac에서 대신 페어링하거나 도우미를 실행하지 않았습니다.
- 서로 다른 텍스트 10회를 복사해 릴레이 수신 내용과 대조했습니다. 키보드가 내려가거나 편집기 포커스가 바뀐 사례는 없었습니다.
- PNG/JPEG는 원본 바이트와 일치했습니다. 잘못된 형식·초과 크기·초과 해상도는 거부됐고, 반대 방향의 텍스트·사진 붙여넣기와 재전송 방지도 확인했습니다.
- 실제 재부팅에서 첫 잠금 해제 전에는 도우미가 실행되지 않았습니다. 잠금 해제 후 부팅 복구 요청부터 실제 복사 감지 준비까지 약 1.45초였고, 이후 새 텍스트 3회가 전달됐습니다. 이 시간은 해당 에뮬레이터에서 관찰한 값입니다.
- 도우미 프로세스 강제 종료 후 자동 복구와 새 텍스트 2회 전달을 확인했습니다. 사용자가 홈에서 중지한 뒤 재부팅한 경우에는 첫 잠금 해제 후에도 브리지와 도우미가 실행되지 않았습니다.
- Android 계측 테스트 5개, 도우미 생명주기 회귀 테스트 12개, 기존 호스트 테스트와 어댑터 경계의 거부 검사 14개가 통과했습니다.

위 결과는 2026-09-13 에뮬레이터 검증 범위입니다. Android 11/12의 수동 연결, x86_64 네이티브 실행, 업무 프로필은 실제 실행 범위에 포함되지 않았습니다. 이전 Shizuku 버전의 Galaxy 결과는 [이전 기록](SHIZUKU.md)이며 새 구현의 실기기 증거로 간주하지 않습니다.

## Galaxy 확인 및 남은 항목 · 2026-09-14

Galaxy SM-S948N / Android 16 / API 36에 기존 데이터를 유지하여 업데이트했습니다. Samsung 설정과 브리지를 분할 화면으로 열어 실제 시스템 코드로 페어링했고, 새 내장 도우미가 shell UID 2000으로 실행됐습니다. 서버 설정과 암호화된 인증 정보의 설치 전후 지문은 동일했습니다.

최초 시작 시 자동 검색이 과거 무선 디버깅 포트를 선택하는 문제를 실제 디버거로 확인했습니다. 이제 같은 휴대폰의 검색 결과 중 닫힌 포트를 건너뛰고, 127.0.0.1에 연결 가능한 포트를 선택합니다. 회귀 테스트는 수정 전 2개 실패에서 수정 후 5개 모두 통과했습니다. 수정한 APK의 SHA-256은 `40042909e8cff6c292f54c02161fa43597d63f97e038d0e0798bdaacba4a86c4`입니다.

- 실제 Mac 앱까지 텍스트 10/10회 전달됐고, 입력 앱 포커스 이탈과 삼성 키보드 숨김은 각각 0회였습니다. 복사 호출 자체는 2–6ms였습니다.
- ADB 터치부터 Mac 검사기 확인까지 374–719ms, 중앙값 499ms였습니다. 이 값은 도구 실행 비용을 포함하며 순수 네트워크 지연이 아닙니다.
- Galaxy→Mac PNG 3701bytes / JPEG 3999bytes는 원본 SHA-256과 일치했습니다.
- Mac→Galaxy JPEG는 원본과 동일하게 붙여넣어졌지만, Mac 클립보드 변경 횟수 검사에서 재전송 의심이 발생했습니다. 사진 양방향 회귀 검증이 완전히 통과한 상태로 간주하지 않습니다.
- 사용자에게 폰을 돌려주기 위해 추가 실기기 조작을 종료했습니다. 재부팅·잠금·도우미 강제 종료 복구는 이 빌드의 Galaxy에서 검증하지 않았고, 자동 복구 옵션도 켜지 않았습니다. 외부 Shizuku 앱은 삭제하지 않았지만 새 도우미의 실행 경로에는 사용하지 않았습니다.

검증용 앱 두 개와 호스트 무선 ADB 연결을 정리하고, 브리지와 내장 도우미는 연결 상태로 유지했습니다.
